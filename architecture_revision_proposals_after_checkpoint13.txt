Proposed corrections for the next ingestion-architecture revision
=================================================================

Purpose
-------

This is an editing guide, not a replacement architecture document.  Each
proposal identifies its destination by section title and nearby wording rather
than by a line number.  The explanation records why the current text is false,
incomplete, or liable to misinterpretation.  The final block is the proposed
text to insert or substitute.

The proposals are derived from the implemented code, its tests, and the public
work records.  They deliberately paraphrase, rather than reproduce, the
private architecture source.


1. Discovery
============

1.1 Discovery philosophy and authoritative snapshots
----------------------------------------------------

Location
~~~~~~~~

In "Source discovery", insert immediately after the opening paragraph that
defines the source-discovery block, before the paragraph beginning with the
daily scheduling policy.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The step list describes the mechanics but not the safety rule that governs
them.  The implementation treats a provider response as authoritative only
after the whole provider-specific snapshot has been retrieved and validated.
It never reconciles a known partial response.  This is essential because an
apparently successful empty, truncated, or internally inconsistent response
would otherwise inactivate valid streams.  Discovery also refreshes registry
membership and descriptive metadata; it does not fetch or publish images.

Text to insert
~~~~~~~~~~~~~~

Discovery is a finite, snapshot-oriented registry-maintenance workflow, not an
image-acquisition workflow.  For each source network it first obtains and
validates a complete provider-specific snapshot, then normalizes that snapshot
and reconciles it transactionally with the registry.  A response known to be
partial, truncated, malformed, or internally inconsistent must fail before
reconciliation.  New entities are inserted, returning entities may be
reactivated, current provider metadata are refreshed, entities absent from a
complete authoritative snapshot may become inactive, and manual blacklisting
is never overridden.  Images are neither downloaded nor published during
discovery.  Provider-specific completeness checks and eligibility rules are
kept in the network connector, while identifier stability and registry status
transitions are shared.


1.2 Corrected coordinates and country enrichment are not implemented pilot steps
-------------------------------------------------------------------------------

Location
~~~~~~~~

In "Source discovery", replace the retrieval-step bullet that retrieves
corrected coordinates from downstream users, remove the later bullet that
updates those corrected coordinates, and replace the complete numbered
"country updating step".  Also revise the closing package-description sentence
that currently lists country-code retrieval as a shared discovery utility.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The schema reserves corrected-coordinate fields, but the discovery workflows
do not retrieve downstream corrections and there is no implemented shared
GeoNames country lookup.  Windy is filtered with provider country information,
Fintraffic is assigned FI because it is a validated national collection, and
Skaping retains cameras with no provider country instead of inventing one.
Presenting corrected-coordinate and generic country enrichment as executed
steps overstates the pilot.

Text to replace it with
~~~~~~~~~~~~~~~~~~~~~~~

Corrected-coordinate ingestion and generic coordinate-to-country enrichment
remain extension points rather than executed pilot steps.  Discovery preserves
the corresponding schema fields but does not populate them from downstream
users.  Country handling is provider-specific: Windy uses the country returned
by its discovery response, Fintraffic uses FI for its validated national
dataset, and Skaping applies member-country filtering only when the provider
supplies a valid country code.  A Skaping camera without provider country data
is retained with a null country.  A future generic country-enrichment service
must be added explicitly before it is included in the discovery sequence.


1.3 Altitude enrichment is resumable and non-fatal
--------------------------------------------------

Location
~~~~~~~~

In "Source discovery", replace the numbered altitude-updating step, which
currently describes altitude lookup as if every eligible value were completed
within the current discovery run.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The shared Open-Meteo elevation pass is bounded by configuration and external
service allowance.  Reliable provider altitude is retained, Fintraffic's
observed geometry value 0.0 is kept only in raw metadata, and unresolved sites
remain null for later daily runs.  Lookup failure does not invalidate a
successfully reconciled provider snapshot.  A standalone resumable command is
also available.

Text to insert
~~~~~~~~~~~~~~

After a successful non-dry-run reconciliation, discovery may invoke the shared
altitude-enrichment pass for sites with valid coordinates and missing
altitude.  A reliable provider altitude takes precedence; an explicitly
untrusted provider value, including the observed Fintraffic geometry value
0.0, is retained only in raw provider metadata.  Elevation requests are
bounded, paced, and validated.  Successful values are written only if the
site, null altitude, and original coordinates still match.  Missing, partial,
throttled, or failed results remain null and are retried by later discovery
runs, so an external elevation-service limit does not make provider discovery
fail.  The same enrichment can be resumed independently for one network with
the standalone altitude command.


1.4 Windy uses hybrid country listings and geographic discs
-----------------------------------------------------------

Location
~~~~~~~~

In the provider section "Windy discovery", replace the paragraph stating that
European discovery executes a configured set of geographic discs.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Using discs for all 33 members would waste daily provider requests.  Live
comparison showed that complete country pagination is coherent for countries
below Windy's 1,000-result cap.  Only countries above that cap require the
configured disc network.  Results are deduplicated by provider webcam ID, and
the precise overseas scope is only what the configured country/disc coverage
actually reaches.

Text to insert
~~~~~~~~~~~~~~

Windy European discovery uses a hybrid completeness strategy.  It first reads
the provider total for every configured EUMETNET member country.  A country at
or below the 1,000-result listing limit is retrieved through complete country
pagination.  A country above that limit is retrieved through its configured
overlapping geographic discs, with the country filter retained.  All results
are merged by Windy webcam identifier before normalization.  The committed
pilot coverage uses 40 km discs for AT, CH, CZ, DE, ES, GB, IT, and NO, and
50 km discs for FI and FR; the other configured members use country listings.
This configuration defines the actual geographic scope and must not be read as
an independent guarantee that every overseas territory is covered.


1.5 Windy status, eligibility, and inferred sites
-------------------------------------------------

Location
~~~~~~~~

In "Windy webcam metadata", insert after the paragraph describing tags.  In
the general "Source discovery" site-inference bullet, add a cross-reference to
this provider rule.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Windy's status value fluctuated for cameras that remained recently usable, so
it is not an eligibility signal.  It is still valuable raw source metadata.
Windy also has no provider site entity: new cameras may share an inferred site
only within 10 metres, while existing assignments remain stable.  These
decisions materially affect reconciliation and should not be left implicit.

Text to insert
~~~~~~~~~~~~~~

Windy's provider status is retained unchanged in source-stream JSON metadata
but is not used to activate or inactivate a stream.  Eligibility follows
presence in the validated complete discovery snapshot, the shared registry
transition rules, and manual blacklisting.  A stream absent from one complete
snapshot currently becomes inactive; no Windy-specific absence grace state is
implemented.  Because Windy exposes no stable parent-site entity, a newly
discovered camera may reuse an inferred Windy site only when its coordinates
are within the configured 10 metre colocation threshold.  Existing site
assignments remain stable, and every stream retains its own provider
coordinates in raw metadata.


1.6 Fintraffic discovery requires list and station-detail requests
------------------------------------------------------------------

Location
~~~~~~~~

In "Fintraffic discovery", replace the description that treats the station
list alone as sufficient, including the sentence suggesting that details may
be completed later.  Replace the documented request-header spelling wherever
it is still written as "Fintraffic-User".

Why the current text is false or incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The compact station list establishes authoritative membership but omits the
descriptive station and preset fields required by the registry.  The
implemented discovery therefore retrieves every eligible station detail in
the same run and rejects an incomplete detail set.  The live official header
is Digitraffic-User.

Text to insert
~~~~~~~~~~~~~~

Fintraffic discovery first retrieves the complete station FeatureCollection
using the required `Digitraffic-User` application-identification header.
Stations are eligible when `collectionStatus` is `GATHERING`, and presets are
eligible only when `inCollection` is true.  The list response is authoritative
for membership but its compact preset records are not a complete metadata
snapshot.  Discovery consequently performs one paced detail request for every
eligible station during the same run.  Missing or malformed required detail
aborts before reconciliation.  The normalized site metadata retains fields
such as purpose, camera type, collection interval, municipality, province, and
road address; stream metadata retains presentation name, direction,
resolution, and image URL.  One station maps to one site, one preset maps to
one source stream, and no JPEG is downloaded by this workflow.


1.7 Skaping discovery completeness and point-of-view scope
----------------------------------------------------------

Location
~~~~~~~~

In "Skaping discovery", insert after the paragraph defining the point of view
as the ingestion unit and selecting image types.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The implementation added explicit response-envelope validation and a minimum
camera-count safeguard after live testing.  It stores the full camera and
point-of-view metadata, excludes non-image views, and legitimately permits
sites without streams.  These safeguards are important because the single
summary response is the authoritative snapshot.

Text to insert
~~~~~~~~~~~~~~

The Skaping summary response is accepted only in one of the validated camera
array envelopes and must contain at least the configured minimum number of
cameras (20 in the pilot).  A malformed or unexpectedly small response fails
before reconciliation so it cannot inactivate the stored collection.  One
provider camera maps to one site and each `image` point of view maps to one
source stream using rendition `mini`; video, frame, and other point-of-view
types are excluded.  A camera with no image point of view remains a valid site
without a stream.  Full camera metadata and full selected point-of-view
metadata, including labels, titles, tags, customer context, timezone, and
public-page descriptors when supplied, are retained as provider JSON.


1.8 Discovery observability for short-lived jobs
------------------------------------------------

Location
~~~~~~~~

In "Source discovery", replace the final metric-emission bullet and extend the
closing package-description paragraph.  The operational-observability section
should cross-reference the same rule.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

All three discovery jobs commonly finish between Prometheus scrapes.  Their
metrics are therefore persisted through Pushgateway rather than exposed only
by the transient process.  Event series accumulate, state gauges are replaced,
and metric delivery is deliberately non-fatal after a committed registry
transaction.

Text to insert
~~~~~~~~~~~~~~

Each discovery run records its result and duration, provider request outcome,
duration and throttling, source streams seen, inserted, refreshed and
inactivated, current registry status counts, and the latest successful run.
Because discovery processes are short lived, they publish these metrics to a
persistent Pushgateway using only the bounded source-network grouping key.
Event counters and histograms are added across runs, while latest-run and
current-status gauges are replaced after success.  Failure to publish metrics
is reported in structured output but does not roll back or relabel an already
committed registry update as a discovery failure.


Discovery consistency check
---------------------------

The proposed discovery text is consistent with the three current workflows,
the shared transactional registry update, shared altitude enrichment, and the
three discovery dashboards.  It intentionally does not claim that corrected
coordinates or generic country lookup are implemented.  It also keeps image
freshness and image download out of discovery; those belong to ingestion.


2. Image ingestion
==================

2.1 Ingestion philosophy: continuous, provider-aware, shared after download
---------------------------------------------------------------------------

Location
~~~~~~~~

In "Image ingestion", insert after the two opening paragraphs and before the
paragraph introducing database state variables.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The current text describes the shared pipeline, but not the boundary between
provider-specific and common behavior or the pilot's preference for bounded
duplicate delivery over durable local replay.  That boundary explains why the
three workers share state, transformation, storage, MQTT, and observability
while using different freshness request shapes.

Text to insert
~~~~~~~~~~~~~~

Ingestion is a continuous, best-effort, at-least-once pipeline.  Each network
has one independently supervised worker and retains only the provider-specific
logic needed to select due streams, assess freshness, obtain an image, and
validate provider metadata.  Once a source image and its observations are
available, all networks use the same in-memory validation, transformation, S3
upload, MQTT publication, state-batching, and observability principles.  S3
upload must complete before MQTT publication.  The pilot accepts that an
ambiguous process, S3, or MQTT failure may cause a deterministic object to be
uploaded again or a QoS 1 notification to be repeated; it does not retain a
durable local image outbox for replay.


2.2 Replace the legacy state-variable description with the five-field model
----------------------------------------------------------------------------

Location
~~~~~~~~

In "Image ingestion", replace the paragraph beginning with the purpose of the
database ingestion-state variables.  Replace later occurrences of
`last_provider_image_marker`, `last_freshness_query_timestamp`, and
`ema_download_period` in the workflow description.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The current schema deliberately has five ingestion-state fields.  The local
download timestamp is not the primary due guard, and the old EMA name no
longer describes the estimator.  Observations are persisted only for a job
that made a download decision, so timestamp and marker components cannot be
acknowledged piecemeal in different epochs.

Text to replace it with
~~~~~~~~~~~~~~~~~~~~~~~

The source-stream ingestion state is limited to five fields:

1. `last_observed_provider_timestamp`, the newest provider timestamp accepted
   with a download decision;
2. `last_observed_image_marker`, the newest opaque image marker accepted with
   that decision when the provider exposes one;
3. `last_download_timestamp`, the local time at which the download attempt was
   decided;
4. `last_processed_timestamp`, the local timestamp used in the name of the
   most recent image whose transformation, S3 upload, and MQTT publication all
   completed; and
5. `estimated_source_stream_period`, the learned provider update-period
   estimate.

Provider observations that do not lead to a download decision are not written.
When a download is decided, its available timestamp, marker, local decision
time, and eligible period candidate form one state transition even if the body
or later pipeline fails.  The processed timestamp advances only after complete
publication.  This distinction permits a failed pipeline to be retried without
repeatedly treating the same provider observation as newly observed.


2.3 Due-stream selection uses two independent guards
----------------------------------------------------

Location
~~~~~~~~

In "Image ingestion", replace epoch step 1, which currently selects streams
from status and elapsed time since the last successful download.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Due selection is based on last successful processing and the latest persisted
provider timestamp/period estimate.  It is not based solely on
`last_download_timestamp`.  Network-specific minimum polling floors were added
after live latency and request-volume experiments.

Text to insert
~~~~~~~~~~~~~~

At the start of an epoch, the worker queries active streams and applies two
independent guards.  First, a stream is eligible when it has never completed
publication or when

    now >= last_processed_timestamp + minimum_ingestion_interval.

Second, it is eligible when either its provider timestamp or period estimate is
missing, or when

    now >= last_observed_provider_timestamp
           + max(minimum_polling_interval,
                 polling_interval_factor
                 * estimated_source_stream_period).

The current polling factor is 0.7.  The pilot minimum polling intervals are
540 seconds for Windy, 480 seconds for Fintraffic, and 240 seconds for Skaping;
the independent minimum successful-publication interval is 300 seconds.  Null
state makes the corresponding guard pass.  `last_download_timestamp` is an
audit and period-learning state value, not the due-selection anchor.


2.4 Epoch timing, bounded concurrency, and deterministic startup staggering
---------------------------------------------------------------------------

Location
~~~~~~~~

In "Image ingestion", insert after the definition of an ingestion epoch and
replace the simple statement that every epoch creates `N_threads`.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The implementation separates per-stream ingestion timing from the minimum
epoch start-to-start period, supports deterministic startup staggering, and
uses measured per-network thread and database-pool limits.  These controls
avoid a cold-start download wave without fabricating database history.

Text to insert
~~~~~~~~~~~~~~

An epoch covers due selection, any epoch-wide provider refresh, bounded
concurrent source jobs, collection of every result, and the final batched state
write.  Its duration is measured across that complete interval.  The minimum
epoch start-to-start period is independently configured and is 15 seconds in
the pilot; it is not a per-stream download interval and does not impose a
five-minute sleep.  Provider jobs run in a bounded thread pool and use a
bounded database connection pool, with limits configured independently for
each network.

At process startup an optional deterministic phase, derived from a fixed seed
and source-stream identifier, spreads each stream's first release across a
600-second window.  This phase exists only in worker memory and does not invent
database timestamps.  Period candidates from each stream's first staggered
release are discarded so the artificial startup phase cannot train the source
period estimate.


2.5 Windy freshness is batched and timestamp-only
-------------------------------------------------

Location
~~~~~~~~

In the generic per-job freshness bullets and the provider section "Windy
freshness detection", replace the statement that one identifier request is
necessarily made by each source job.  Retain the documented meaning of
`lastUpdatedOn`.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The production Compose worker now batches Windy freshness for up to 50 known
webcam IDs per API request before running source jobs.  It does not use
geographic discovery discs.  Windy exposes a provider timestamp but no
separate opaque image marker in the retained state.

Text to insert
~~~~~~~~~~~~~~

For Windy, the epoch refreshes current image references in batches of at most
50 explicitly known webcam identifiers.  This is an ingestion optimization
and does not execute geographic discovery.  Each returned reference supplies
`lastUpdatedOn`, interpreted as a provider-availability timestamp, and the
selected current image URL.  Windy persists that timestamp when a download is
decided and leaves the opaque marker null.  An unchanged timestamp stops the
job before image download.  Missing IDs or failed batches are controlled
freshness-query errors and do not invalidate the accounting of other batches
or source jobs.


2.6 Fintraffic freshness uses a bulk timestamp and a GET-time ETag
------------------------------------------------------------------

Location
~~~~~~~~

Replace the orange/conditional Fintraffic statements in both the provider
freshness paragraph and the generic per-job workflow.

Why the current text is false or unresolved
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The pilot made the provider choice.  One station-data snapshot supplies
`measuredTime` for the epoch; ETag is learned only from the JPEG GET.  The
response `Last-Modified` must validate the bulk timestamp, and an unchanged
ETag causes the already downloaded body to be discarded.

Text to insert
~~~~~~~~~~~~~~

For Fintraffic, a non-empty epoch retrieves one bulk station-data snapshot.
Each due preset obtains its provider timestamp and current JPEG reference from
that snapshot.  A source job performs the full JPEG GET and requires a valid
ETag plus a `Last-Modified` timestamp coherent with the bulk observation.  A
missing or inconsistent `Last-Modified` is treated as an image-access race or
unavailable image and is deferred to a later epoch.  If the downloaded ETag
equals `last_observed_image_marker`, the body is discarded as unchanged; the
download decision and observations remain eligible for the epoch-end state
batch, but processed state does not advance.  This also excludes observed
placeholder responses that cannot be validated with the expected timestamp.


2.7 Skaping freshness uses final-object ETag and Last-Modified
-------------------------------------------------------------

Location
~~~~~~~~

Replace the unresolved orange alternatives in "Skaping freshness detection
and image archives" and "Image download and rendition choice", and update the
generic freshness-marker bullet.

Why the current text is unresolved
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A bounded comparison was completed.  The archive endpoint is heavier and does
not directly identify the point of view.  The implementation resolves the
stored latest-media mini pointer with a body-free request, uses final-object
ETag as marker, and uses Last-Modified as provider-availability timestamp.

Text to insert
~~~~~~~~~~~~~~

For Skaping, discovery stores the selected point of view's
`latest_media`/`mini` pointer.  Freshness resolution follows that pointer
without downloading the body and requires the final object's ETag.  The ETag
is the opaque image marker; `Last-Modified`, when valid, is the provider
availability timestamp used for scheduling, latency, and period learning, not
a claim about physical capture time.  A changed object is accepted only if the
subsequent GET repeats the expected ETag.  The sanitized resolved target path
is retained in source-image provider metadata and can be included in the MQTT
message.  The archive endpoint is not queried by the continuous worker.


2.8 Source-period estimation replaces download-gap EMA
------------------------------------------------------

Location
~~~~~~~~

Replace the per-job `ema_download_period` formula and initialization paragraph,
and replace later uses of that term in the image-ingestion and database
sections.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The stored quantity was renamed because it estimates provider update cadence,
not download cadence.  It is learned from consecutive distinct provider
timestamps.  Windy uses a bounded running minimum with a five-minute floor;
Fintraffic and Skaping retain the recurrent formula.  Updates are epoch-level,
not immediate thread writes, and a deterministic rare direct replacement is
being added to escape an anomalously stale minimum.

Text to insert
~~~~~~~~~~~~~~

`estimated_source_stream_period` estimates the interval between distinct
provider update timestamps.  A job can propose a candidate only when it has a
new valid provider timestamp and made a download decision.  Windy updates the
estimate with the minimum of the previous estimate and the new positive
provider-timestamp gap, bounded below by 300 seconds.  Fintraffic and Skaping
use the configured recurrent smoothing rule over the same provider-timestamp
gaps.  The algorithm-neutral field name permits those network-specific update
rules without implying that the value is always an exponential average of
local downloads.

To avoid retaining an anomalous old estimate indefinitely, a shared
deterministic SHA-256 decision over source-stream ID and canonical provider
timestamp selects approximately one eligible update in a configurable N to
replace the estimate directly with the latest positive gap.  N defaults to
250 independently for each network.  Direct replacement requires an existing
estimate, so null state still passes through normal initial learning.


2.9 Period and state updates occur once at epoch end
---------------------------------------------------

Location
~~~~~~~~

Replace the per-thread database-update bullet following source-level
observability, and insert after the list of per-job operations.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Source threads no longer write ingestion state individually.  They return
state transitions to the coordinator, which performs one batch at epoch end.
Period updates retain first-epoch, startup-stagger, and overlong-epoch guards;
other download-decision state must still be stored when a period candidate is
discarded.

Text to insert
~~~~~~~~~~~~~~

Each source job returns, rather than writes, its optional download-decision
state, successful processed timestamp, and period candidate.  After every
future has been collected, the epoch coordinator applies all returned state
transitions in one database batch.  Download-decision and processed state are
written independently of period-candidate eligibility.  Period candidates are
not applied during epoch 1, for a stream's first deterministic stagger release,
or when total epoch duration is at least the network's minimum ingestion
interval.  These guards preserve startup and overloaded-epoch evidence without
losing the state needed for retries and freshness comparison.


2.10 Synchronous S3 and MQTT delivery replaces the publication outbox
---------------------------------------------------------------------

Location
~~~~~~~~

In the shared ingestion-core list, replace any outbox/replay wording and amend
the S3-upload and MQTT-publication bullets.  Remove the publication-outbox
entity and replay path from diagrams and schema descriptions.

Why the current text is incomplete or obsolete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The experimental durable publication outbox was removed.  Derived bytes are
not stored in PostgreSQL.  S3 uses direct PUT without a preliminary HEAD, then
MQTT is attempted synchronously.  Retry attempts are separate from one final
operation outcome.

Text to insert
~~~~~~~~~~~~~~

After transformation, the worker writes the deterministic object key directly
with an S3 PUT and attached SHA-256 metadata; it does not issue a preliminary
HEAD.  The configured retry loop is contained within this one high-level
upload operation.  Only after S3 success does the worker build and publish the
MQTT notification with QoS 1, again using its configured retry loop.  Each
high-level S3 or MQTT operation records exactly one final success or failure,
while every retry attempt actually started is counted separately.  No derived
image payload or delivery stage is retained in PostgreSQL, and there is no
automatic replay command.  A later due job provides best-effort recovery, with
possible idempotent S3 overwrite or duplicate MQTT notification accepted by
the pilot.


2.11 One unexpected source-job exception does not invalidate an epoch
---------------------------------------------------------------------

Location
~~~~~~~~

Insert after the bounded-thread-pool description and before the shared-core
description.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Concurrent job collection has an explicit defensive boundary.  Without it,
one unexpected exception escaping a future would abort remaining result
collection and make epoch state and metrics incomplete.

Text to insert
~~~~~~~~~~~~~~

The coordinator catches unexpected exceptions independently around every
completed source-job future.  It logs the affected source-stream identifier
and epoch, records a controlled `internal_error` job outcome, and continues
collecting all remaining futures.  Expected provider, download,
transformation, storage, and publication failures remain ordinary structured
job results.  One defective stream therefore cannot invalidate the complete
epoch's accounting or suppress unrelated state transitions.


Ingestion consistency check
---------------------------

The proposed ingestion text uses the same five-field and epoch-end batching
philosophy for all three networks.  Only the acquisition point of timestamp
and marker differs: Windy supplies timestamp in batched freshness metadata,
Fintraffic supplies timestamp in its bulk snapshot and ETag during GET, and
Skaping supplies ETag and Last-Modified while resolving the current object.
The text preserves the first-epoch, stagger-release, and long-epoch estimator
guards; it does not reintroduce immediate thread writes or the removed outbox.


3. Database
===========

3.1 Update the source-stream schema and database role
-----------------------------------------------------

Location
~~~~~~~~

In "Ingestion database", replace the paragraph and diagram annotations that
list three legacy ingestion-state fields.  In the schema appendix, replace the
`SOURCE_STREAM` entity field list and the explanations of its state columns.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The physical table now uses the five-field state model described above and no
longer contains a publication outbox.  The explicit columns are shared across
networks; provider-specific descriptive data remain JSON.  The diagram and
schema appendix otherwise teach an obsolete database contract.

Text to insert
~~~~~~~~~~~~~~

The physical pilot database contains the shared `network`, `site`, and
`source_stream` tables.  The source-stream table stores stable provider and
registry identifiers, selected rendition, registry status, provider JSON, and
the following explicit ingestion state:

    last_observed_provider_timestamp timestamptz NULL
    last_observed_image_marker text NULL
    last_download_timestamp timestamptz NULL
    last_processed_timestamp timestamptz NULL
    estimated_source_stream_period double precision NULL

The meaning and update boundary of these fields are defined by the five-field
ingestion model.  There is no physical derived-stream, derived-image,
notification, or publication-outbox table.  Derived identifiers and object
keys are deterministic, image bytes live in S3, and notifications are sent
through MQTT.


3.2 Due reads and state writes reflect epoch-end batching
--------------------------------------------------------

Location
~~~~~~~~

In "Ingestion database", replace the paragraph that selects streams using
`last_download_timestamp`, and replace the later paragraph that presents
epoch-end state batching as a possible future optimization.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The adaptive two-guard query and epoch-end batched writes are already
implemented.  They are correctness choices as well as performance choices:
one provider observation is committed atomically, after all concurrent jobs
have returned.

Text to insert
~~~~~~~~~~~~~~

At epoch start, each network worker performs one joined site/source-stream due
query using active status, the successful-publication guard, and the adaptive
provider-timestamp guard.  The query also returns all site and stream metadata
needed by source jobs and notification construction.  Source threads perform
no ingestion-state writes.  Their optional state transitions are collected in
memory and applied through one transactional batch at epoch end.  This reduces
connection churn and prevents a timestamp and marker from one accepted
freshness observation being committed separately.


3.3 Pooled connections must be returned in idle transaction state
------------------------------------------------------------------

Location
~~~~~~~~

In "Ingestion database", insert after the discussion of concurrent PostgreSQL
access by provider workers.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Psycopg begins transactions even for ordinary reads, and a database error
leaves a connection unusable until rollback.  The custom bounded pool now has
an explicit hygiene rule so an unrelated job cannot inherit an open or aborted
transaction.

Text to insert
~~~~~~~~~~~~~~

Before a borrowed PostgreSQL connection is returned to the worker pool, its
transaction status must be IDLE.  Any open or failed transaction is rolled
back.  If rollback cannot restore an idle connection, that connection is
closed, removed from the pool, and replaced only when later demand requires a
new slot.  Pool wait, rollback, discard, and replacement behavior are
observable.  Provider HTTP and image processing do not hold a database
connection unnecessarily.


3.4 PostgreSQL backup format, namespace, and verification
---------------------------------------------------------

Location
~~~~~~~~

Replace the short final paragraph of "Ingestion database" describing
`database_backup.py`.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The implementation chose a concrete EWC S3 namespace and verification
contract, and tied conservative retention to successful backup.  The dump is

Text to insert
~~~~~~~~~~~~~~

The backup job creates a full PostgreSQL custom-format dump with a compatible
PostgreSQL 16 client and stores it in the configured S3 tenancy below

    backups/postgresql/YYYY/MM/DD/

3.5 Restore is explicit, verified, and never an automatic crash response
--------------------------------------------------------------------------

Location
~~~~~~~~

In "Restart and recovery policies", replace the final database-restoration
paragraph and add a cross-reference from "Ingestion database".

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The operator tool and safety protocol now exist.  Ordinary PostgreSQL failure
restarts the container against its existing volume; the service must not infer
corruption and overwrite live state automatically.  Restore validates both
the object and resulting registry, and workers stay stopped after failure.

Text to insert
~~~~~~~~~~~~~~

A PostgreSQL process failure first triggers an ordinary container restart that
reuses the persistent data volume.  Database restoration is never selected
automatically from a health-check failure.  It is an explicit operator-approved
maintenance command.  The command accepts only canonical backup keys, requires
the selected key to be repeated exactly as confirmation, verifies S3 length
and SHA-256 metadata, validates the custom archive, restores it, and checks the
required schema and registry invariants.  A separate validation mode restores
into a disposable database.  Live workers are stopped before replacement and
are restarted only after successful validation; they remain stopped if any
restore step fails.  Restored ingestion state, including the learned period,
is preserved.


Database consistency check
--------------------------

The database proposals match migrations 005--007: the outbox is absent, the
five ingestion-state fields are authoritative, and the old EMA column has the
algorithm-neutral period name.  They also separate ordinary container restart
from destructive restore and do not claim automatic corruption diagnosis.


4. Storage and maintenance
==========================

4.1 Image cleanup uses exact age and a transformation scope
-----------------------------------------------------------

Location
~~~~~~~~

In "Image storage" / "Storage cleanup", replace the paragraphs describing
deletion of complete date prefixes older than the previous UTC day and the
resulting 24-to-48-hour retention range.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The implementation parses the timestamp from each strictly canonical image
key and compares it with an exact age cutoff.  It defaults to one explicit
transformation prefix, with an operator option for all recognized
transformation prefixes.  This avoids deleting unrelated consumers' objects
or backup keys in a shared bucket.

Text to insert
~~~~~~~~~~~~~~

Image-spool cleanup lists the configured S3 namespace and recognizes only
canonical derived-image keys.  It derives age from the UTC timestamp encoded
in each validated key and selects objects older than the exact configured
number of hours; the production value is 24 hours.  By default an invocation
must name one transformation prefix, such as `T0V0`.  An explicit
`all-transformation-prefixes` option may cover every recognized canonical
transformation layout.  Unknown, malformed, non-image, and PostgreSQL-backup
keys are skipped.  Dry-run, result limits, paginated listing, batched deletion,
and structured metrics provide operational safety and bounded validation.


4.2 Backup retention runs only after a verified new dump
--------------------------------------------------------

Location
~~~~~~~~

Insert after the revised database-backup paragraph and cross-reference it from
the maintenance sequence.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The architecture does not currently specify dump cleanup.  The implemented
policy intentionally retains monthly recovery points and deletes only a very
conservative same-month predecessor after a verified current dump exists.

Text to insert
~~~~~~~~~~~~~~

Only after a new database dump has been uploaded and verified does the backup
job run retention cleanup.  It may remove the latest preceding available
daily dump only when that dump belongs to the same calendar month as the new
verified dump.  On the first day of a month, the final dump from the preceding
month is retained.  Under regular daily execution this keeps the newest dump
for the current month and one final recovery point for each preceding month.
Unexpected or malformed backup keys are never deleted automatically.


4.3 Maintenance is cleanup-first, non-overlapping, and failure-tolerant
------------------------------------------------------------------------

Location
~~~~~~~~

In "Deployment and orchestration model" / "Orchestration", replace the four
independently scheduled one-shot workflow bullets and the later paragraph on
their failure handling.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The retained pilot uses one systemd-triggered maintenance sequence rather than
independent discovery, cleanup, and backup timers.  Cleanup was deliberately
moved first after a missed cleanup allowed storage exhaustion during a live
run.  Every step must still be attempted when an earlier step fails.

Text to insert
~~~~~~~~~~~~~~

One daily systemd timer triggers a non-overlapping best-effort maintenance
sequence.  The sequence acquires a process lock and then attempts, in order:

1. transformation-scoped image-spool cleanup;
2. Windy discovery;
3. Fintraffic discovery;
4. Skaping discovery; and
5. verified PostgreSQL backup followed by conservative dump cleanup.

Each step runs in its own short-lived application container with a configured
timeout.  A failure or timeout is recorded but does not suppress later steps;
the aggregate sequence fails only after every step has been attempted.
Cleanup is first because failure to enforce retention can exhaust storage and
prevent discovery, backup, and newly started Python processes.  The lock
distinguishes an overlapping invocation from inability to create or open the
lock file.


Maintenance consistency check
-----------------------------

The revised maintenance order matches the pilot runner and its failure tests.
Image cleanup cannot select backup keys; backup cleanup is part of a verified
backup operation and is not confused with spool cleanup.  Discovery failure
therefore cannot prevent either storage protection already attempted or the
later backup attempt.


5. Deployment, restart, and recovery
====================================

5.1 Compose owns application workers; systemd owns boot and schedule
--------------------------------------------------------------------

Location
~~~~~~~~

In "Deployment and orchestration model", replace the paragraphs assigning
long-running application restart and per-worker journals to templated systemd
services, including the example service names.  Retain the common-image
containerisation paragraph.

Why the current text is false
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

After containerization, the three ingestion workers are independent
long-lived Docker Compose services.  Compose owns their restart, networking,
secrets, resource bounds, dependencies, and health checks.  Systemd no longer
runs their Python processes directly.

Text to insert
~~~~~~~~~~~~~~

Docker Compose defines the persistent PostgreSQL, MQTT, monitoring, and three
network-specific ingestion-worker containers.  Windy, Fintraffic, and Skaping
workers are independent services built from the same application image and
started with network-specific commands and configuration.  Compose owns their
service dependencies, internal networking, mounted secrets, CPU and memory
limits, health checks, graceful-stop allowance, and `unless-stopped` restart
policy.  A failed worker can therefore restart without restarting the other
networks.  Systemd is limited to VM-boot integration for the Compose stack and
to the daily maintenance trigger; it does not supervise the worker Python
processes directly.


5.2 Health, restart evidence, and graceful stop
-----------------------------------------------

Location
~~~~~~~~

In "Restart and recovery policies", replace the application-service restart
paragraph and extend the observability cross-reference.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Each worker has a network-specific readiness window to accommodate legitimate
long epochs.  Docker restart count and replacement health are both needed to
prove recovery; health alone could describe the old process.  Signals stop new
epoch intake and allow the active epoch to finish until the container stop
policy expires.

Text to insert
~~~~~~~~~~~~~~

Each worker exposes liveness/readiness and Prometheus metrics on its own
endpoint.  Readiness requires recent successful epoch completion, with a
ten-minute Windy window and five-minute Fintraffic and Skaping windows by
default so legitimate long epochs are not mistaken for crashes.  Compose
restarts an unexpectedly exited worker.  A recovery check must observe both an
increased container restart count and a healthy replacement process; health
alone is insufficient evidence.  On SIGINT or SIGTERM the worker stops taking
new epochs and lets the active epoch finish.  Compose's stop grace period is
the outer bound before container-level forced termination.


5.3 Recovery drills do not perform automatic destructive restore
-----------------------------------------------------------------

Location
~~~~~~~~

Insert at the end of "Restart and recovery policies" after the explicit
database-restore policy.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The implemented unquiet drill distinguishes recoverable process/container
faults from operator-approved database replacement.  This boundary should be
architectural, not only a manual-test detail.

Text to insert
~~~~~~~~~~~~~~

Operational drills may terminate one ingestion container and restart the
PostgreSQL container while preserving its volume, then verify independent
worker recovery and maintenance continuity.  Such drills must not infer
database corruption or invoke S3 restoration automatically.  A VM that is
itself unavailable cannot emit its own reliable failure notification;
VM-death detection therefore requires an external observer or uptime service.


Deployment consistency check
----------------------------

The proposed deployment text preserves the intended lightweight single-VM
pilot but moves ownership to the components that actually perform it: Compose
for long-lived containers and restart, systemd for VM boot and one daily
sequence.  It is compatible with later deterministic multi-VM Windy
partitioning because PostgreSQL remains authoritative and worker ownership can
be partitioned without duplicating state.

6.2 Clarify metric philosophy and delivery paths
------------------------------------------------

Location
~~~~~~~~

In "Observability", replace the general paragraph listing custom application
metrics with the following text, then retain the detailed appendix after
updating obsolete names.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

It does not distinguish continuously scraped workers from short-lived batch
jobs, nor the low-cardinality and definitive-operation rules added during

Text to insert
~~~~~~~~~~~~~~

Long-lived ingestion workers expose metrics directly on independent

7. Whole-system workflow philosophy
===================================

Location
~~~~~~~~

In the general architecture overview, insert after the paragraph that names
source discovery and image ingestion as the two main workflows, before the
component diagram is introduced.

Why the current text is incomplete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The document describes the workflows individually but does not state their
operational relationship or failure boundaries.  The implementation now has a
clear continuous path, a finite registry path, and a cleanup-first protective
maintenance path.

Text to insert
~~~~~~~~~~~~~~

The pilot separates three workflow philosophies.  Image ingestion is
continuous and independently supervised per provider; it tolerates controlled
per-stream failures and continues with the remaining work.  Discovery is a
finite, complete-snapshot registry reconciliation; it refuses partial
provider snapshots and never downloads images.  Maintenance is a scheduled,
non-overlapping, cleanup-first best-effort sequence; every step is bounded and
later protective work is attempted even when an earlier step fails.  All
three workflows share the PostgreSQL registry, provider-neutral identifiers,
container image, secrets/configuration model, and observability conventions,
but they do not share a single loop or failure transaction.  PostgreSQL is the
authoritative state store, S3 is the temporary derived-image spool and backup
store, MQTT is the downstream notification interface, Docker Compose owns
long-lived runtime recovery, and systemd owns VM integration and scheduled
maintenance.


Final cross-domain consistency check
====================================

The proposed revision has one consistent ownership model:

- discovery owns authoritative provider membership and descriptive metadata;
- ingestion owns download-decision, processed-publication, and learned-period
  state;
- PostgreSQL owns durable registry and ingestion state but no image payloads;
- S3 owns temporary derived images and verified database dumps in disjoint key
  namespaces;
- MQTT is attempted only after S3 success;
- cleanup protects finite storage before other daily work;
- Compose restarts independent long-lived containers;
- systemd triggers one non-overlapping maintenance sequence; and
- Prometheus/Grafana observe continuous and batch workflows through the
  appropriate scrape or push path.

No proposal requires the unimplemented corrected-coordinate feed, generic
country enrichment, durable publication outbox, automatic database restore,
or outbound email delivery.  Those must remain explicitly deferred unless a
later implementation and validation record supersedes this note.
