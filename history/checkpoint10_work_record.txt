Checkpoint 10 work record - Skaping discovery
==============================================

Status
------

Implemented, fixture-validated, and live-validated locally on 2026-07-23.
Owner acceptance remains pending. This checkpoint discovers and reconciles
Skaping cameras; it does not download, transform, store, or publish images.

Provider model and scope
------------------------

- Network `ska` represents Skaping.
- One provider camera is one registry site.
- One `point_of_views` entry whose type is `image` is one source stream.
- `video`, `frame`, and any other non-image point-of-view types are excluded.
- The selected rendition is `mini`; discovery does not retrieve that image.
- The API key is read from ignored file `.secrets/skaping_api_key` and sent
  only as the `api_key` query parameter.
- A finite timeout, reusable gzip-capable HTTP client, and controlled
  retry/backoff protect the single summary request.

Snapshot validation and normalization
-------------------------------------

The authoritative endpoint is:

    GET https://api.skaping.com/camera/summaryApp?api_key=<secret>

The response must contain one camera array. Explicitly tested top-level forms
are the array itself, `cameras`, `data`, and `data.cameras`. Each camera must
have a stable ID, valid finite latitude/longitude, optional finite altitude,
and a point-of-view array. Each point of view must have a stable ID and
non-empty type.

A malformed response or a camera count below
`SKAPING_DISCOVERY_MIN_CAMERAS` aborts before reconciliation. This prevents a
successful-looking empty or partial response from inactivating the complete
stored provider set.

When the provider supplies a valid country code, non-EUMETNET countries are
excluded. Cameras without a country code remain eligible and retain null
country rather than receiving a coordinate-derived guess. The shared altitude
enrichment pass follows successful reconciliation and fills missing altitudes
within its daily call budget.

Identifiers and metadata
------------------------

- Site IDs follow `ska{camera_id}`.
- Stream IDs use the readable `ska{camera_id}POV{point_of_view_id}` form when
  it fits.
- Provider components are normalized to the registry's alphanumeric ID
  constraint; long values and collision suffixes are resolved
  deterministically within the shared 16-character bound.
- Existing IDs are preserved on repeated discovery.
- Full camera metadata is stored on the site, including provider label,
  customer/customer ID, timezone, coordinates, and any provider fields.
- Full point-of-view metadata is stored on the stream, including label, title,
  URL, tags, and public-page meta fields.
- A previously enriched altitude/country is retained when coordinates are
  unchanged and the current provider snapshot omits it.

Registry behavior
-----------------

The workflow reuses the shared transactional discovery reconciliation:

- new sites/streams are inserted;
- existing metadata is refreshed;
- returning inactive streams are reactivated;
- streams absent from a complete snapshot become inactive;
- blacklisted streams remain blacklisted;
- `--dry-run` retrieves, validates, normalizes, and compares without writing.

Discovery observability
-----------------------

Skaping is the first provider to use
`discovery/shared/discovery_metrics.py`. Because a complete run finishes in
less than one Prometheus scrape interval, the one-shot process pushes
service-level batch metrics to a local persistent Pushgateway. Prometheus
scrapes that gateway, and Grafana provisions the dedicated `Skaping discovery`
dashboard.

The shared metrics cover:

- run success/failure and end-to-end duration;
- source streams seen, inserted, refreshed, and inactivated;
- current active, inactive, and blacklisted registry counts;
- provider summary-request attempts, outcomes, duration, and throttling;
- last successful run time and latest successful duration.

Event counters and histograms accumulate across runs. Current registry gauges
are replaced after each successful run. A Pushgateway outage is reported by
`discovery_metrics_published=false` but does not roll back or fail an otherwise
successful registry transaction. The fixed grouping key is the bounded
`source_network`, not a process or host identifier.

------------------------

The dry run confirmed the provider contract without printing the secret or
complete payload:

- 45 cameras seen and accepted;
- 67 points of view seen;
- 41 image points accepted;
- 26 non-image points excluded;
- no country exclusions.

The first applied run inserted 45 sites and 41 active `mini` streams, with no
inactive or blacklisted streams. Five missing provider altitudes were resolved
by shared enrichment. Four sites legitimately have no image point of view and
therefore do not appear in a site/stream inner join.

The immediate repeat inserted nothing and changed no status. It refreshed all
45 site and 41 stream metadata snapshots, while altitude enrichment had no
remaining eligible sites. SQL inspection found all 45 sites with labels,
customers, timezones, and non-null altitude; all 41 streams were active and
used `mini`.

Because the complete live snapshot contained 45 cameras, the default partial
snapshot safety threshold was raised from one to 20. Owner review and explicit
checkpoint acceptance remain pending.

The GitHub Pages discovery slide records the same snapshot, including
discovery duration, registry and metadata coverage, the most frequent raw tag
tokens, and 33 deduplicated panoramic image views identified across provider
tags, type, and label.

The first instrumented applied run completed in 0.492 seconds. It observed one
successful summary request, 41 source streams seen and refreshed, zero
insertions or inactivations, and registry state of 41 active, zero inactive,
and zero blacklisted streams. The command reported
`discovery_metrics_published=true`; the Pushgateway exposed the expected
series, and Prometheus returned them with `source_network="ska"`.

The focused shared-discovery-metrics, Skaping, and configuration suite passed
