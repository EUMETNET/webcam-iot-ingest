Intended webcam ingestion development plan
===========================================

Purpose and working rules
-------------------------

This document records the intended implementation sequence derived from the
ingestion architecture and the repository inspection performed before
Checkpoint 1.

The following rules apply throughout development:

- Work only on the codex branch unless explicitly instructed otherwise.
- Treat the private architecture document as read-only background material.
- Do not copy or commit the private architecture document.
- Do not commit passwords, API keys, tokens, or S3 credentials.
- Read secrets at runtime from ignored, permission-restricted files.
- Implement only one checkpoint at a time.
- Stop after every checkpoint and provide validation commands.
- Continue only after the repository owner has run or accepted the checkpoint
  validation.
- Implement providers in this order: Windy, Fintraffic, then Skaping.
- Do not use destructive Git commands without first showing the exact command
  and obtaining approval.
- Do not delete PostgreSQL volumes as part of routine validation.

Checkpoint 1 - Local infrastructure and pilot schema
----------------------------------------------------

Status: implemented in commit f9956c0.

Objectives:

- Provide local PostgreSQL and Mosquitto services through Docker Compose.
- Keep host ports on the VM loopback interface for local development.
- Pin the PostgreSQL and Mosquitto container versions.
- Store the PostgreSQL password in an ignored secret file.
- Create the three physical pilot tables: network, site, and source_stream.
- Add schema constraints, foreign keys, indexes, and provider seed rows.
- Add database configuration, a schema health check, and focused tests.

Stop condition:

- PostgreSQL and MQTT start and become healthy.
- The schema health check finds all three tables.
- Database integration tests pass.
- MQTT publish/subscribe works.
- PostgreSQL data survives a normal container restart.
- No secret is present in the Git diff.

The detailed validation commands are stored in:

    manual_tests/sudo_install_and_validation_to_complete_step1

Checkpoint 4 - Shared altitude enrichment
-----------------------------------------

Objectives:

- Add provider-independent altitude enrichment under
  discovery/shared/altitude_lookup.py.
- Add configuration to enable or disable altitude lookup and select the
  Open-Meteo Elevation API endpoint without storing secrets in Git.
- Preserve a reliable provider altitude when one is available.
- Treat missing or explicitly unreliable provider altitude values as
  candidates for enrichment.
- Retrieve approximate altitude from the Open-Meteo Elevation API, based on
  Copernicus DEM GLO-90, for new sites without altitude and known sites whose
  altitude remains missing.
- Batch requests conservatively, enforce explicit timeouts, validate response
  cardinality and numeric values, and apply bounded retry/backoff behavior.
- Leave altitude unset after an unavailable, throttled, malformed, or partial
  elevation response and retry it during a later discovery run.
- Preserve a derived altitude while its source coordinates are unchanged.
- Reset and recompute derived altitude when provider coordinates change.
- Support corrected_altitude enrichment independently when corrected
  coordinates are available, and reset it when those coordinates change.
- Integrate enrichment into Windy discovery before the transactional registry
  update, while preserving --dry-run as a no-write operation.
- Ensure later provider discovery workflows can reuse the same altitude
  enrichment component.

Expected validation:

    uv run pytest tests/discovery/shared tests/discovery/windy -v
    RUN_DATABASE_TESTS=1 uv run pytest tests/database/test_registry_queries.py -v
    uv run python -m discovery.windy.windy_discovery_workflow --dry-run
    uv run python -m discovery.windy.windy_discovery_workflow
    docker compose exec postgres psql -U webcam_ingestion -d webcam_ingestion -c \
      "SELECT count(*) AS sites, count(altitude) AS sites_with_altitude FROM site WHERE network_id = 'win';"

Repeat discovery and confirm that unchanged coordinates preserve the same
altitudes. Exercise an elevation-service failure and confirm that discovery
remains safe, affected altitudes remain null, and the next run retries them.
Stop after validation and wait for approval.

Checkpoint 7 - Operational Windy worker
---------------------------------------

Status: implemented and ready for repository-owner validation on 2026-07-21.

Objectives:

- Add the continuous Windy worker loop.
- Enforce adaptive per-stream polling from the last freshness query using
  `min(max(minimum_ingestion_interval, 0.7 * EMA), 30 minutes)`.
- Bound worker threads, retries, and backoff.
- Enforce a configurable minimum epoch start-to-start period, initially 15
  seconds, as a loop-level safeguard in addition to per-stream polling.
- Default to zero transformation retries, one S3 upload retry, and one MQTT
  publication retry. Reuse the same transformed bytes and identifiers on retry.
- Support graceful shutdown.
- Expose low-cardinality Prometheus metrics.
- Add application health checks.
- Verify restart and state-recovery behavior.
- Process transformation, S3 upload, and MQTT publication synchronously.
  Advance processed freshness state only after the complete pipeline succeeds;
  freshness detection supplies later retries after failures.
- Stabilize Compose operation before adding production systemd units.

Expected validation:

    docker compose --env-file .env up -d postgres mqtt
    uv run pytest tests/ingestion tests/transformation tests/storage \
      tests/notification tests/worker tests/metrics -v
    uv run python -m ingestion.worker --network win --countries DK \
      --max-jobs 2 --epochs 2 --dry-run
    curl --fail http://localhost:8002/metrics
    docker compose restart postgres mqtt
    uv run python -m database.healthcheck

At this point Windy is the first complete provider slice. Stop and wait for
approval before beginning Fintraffic.

Checkpoint 9 - Fintraffic ingestion
----------------------------------

Status: accepted by the repository owner on 2026-07-23.

Objectives:

- Use Fintraffic full-JPEG image URLs.
- Fetch the station-data endpoint once per epoch and use each preset's
  `measuredTime` as both its opaque provider marker and provider timestamp.
- Download a full JPEG only when that marker differs from the stored marker.
- Validate the image response `Last-Modified` against the snapshot marker so a
  metadata/image race is deferred safely to a later epoch.
- Feed changed images through the shared validation, T0V0, S3, and N0V0 MQTT
  pipeline.
- Run a separate Fintraffic worker and metrics endpoint alongside Windy.
- Default Fintraffic freshness and image retry counts to zero.
- Support deterministic initial staggering over a 10-minute window.
- Add tests for changed, unchanged, missing, invalid, race, and transient
  responses.

Expected validation:

    uv run pytest tests/ingestion/fintraffic -v
    just ingest-fintraffic --limit 10 --dry-run
    just ingestion-test-fintraffic 20m staggered

Marker comparison, deterministic identifiers, and database collision tests
must prevent duplicate processing for the same stored marker. Two immediate
bounded commands are not an idempotency test because successful streams become
temporarily not due while never-successful streams remain eligible. The
accepted monitored worker run exercised unchanged markers and durable
publication without duplicate processing. Checkpoint 10 may now begin when
requested.

Discovery observability rollout after checkpoint 10
---------------------------------------------------

The provider-independent implementation begins with Skaping because its
sub-second batch cannot reliably be scraped while it is alive. Persistent
batch metrics are therefore pushed to a local Pushgateway and scraped by
Prometheus. After the parallel Fintraffic ingestion test completes, apply the
same shared functions to discovery in this order:

1. Fintraffic discovery;
2. Windy discovery.

Provider connectors retain only their provider-specific request endpoint and
result observations. Metric names, bounded labels, Pushgateway lifecycle,
Prometheus scraping, and dashboard conventions remain shared. This staged
rollout moves application-level discovery observability forward from
checkpoint 12; checkpoint 12 still owns production systemd supervision,
infrastructure exporters, health alerts, and full orchestration.

Checkpoint 13 - Production orchestration and operational recovery
----------------------------------------------------------------

Objectives:

- Replace bounded validation workers with full configured provider scopes.
- Replace accelerated timers and retention with production schedules.
- Add production secret-file paths and deployment documentation.
- Exercise restart, failure, reboot, backup, and recovery drills.
- Restore a selected dump only as an explicitly approved maintenance action.
- Never automate destructive database restoration or volume deletion.

Implementation sequence:

1. Retain Docker Compose as the application and infrastructure runtime.
   Windy, Fintraffic, and Skaping ingestion are independent long-lived Compose
   services using `restart: unless-stopped`, separate health endpoints, logs,
   and metrics. Systemd provides VM-boot integration and invokes the scheduled
   maintenance sequence; it does not supervise a second set of host workers.

2. Add an explicit database-recovery command. It lists available S3 dumps,
   downloads the selected dump, verifies it before use, stops all ingestion
   workers, restores PostgreSQL, validates the restored schema and registry,
   and restarts the workers. Ordinary PostgreSQL failure continues to reuse
   the persistent data volume and never triggers automatic dump restoration.
   Restoration preserves the learned `estimated_source_stream_period` and
   other ingestion state: the bounded-minimum estimator no longer requires a
   post-restore reset to legacy first-epoch EMA defaults.

3. Implement one non-overlapping production maintenance sequence. A systemd
   timer invokes a sequencer which launches each application operation as a
   short-lived `docker compose run --rm` container. The order is:

       S3 image cleanup
       Windy discovery
       Fintraffic discovery
       Skaping discovery
       PostgreSQL backup and backup-retention cleanup

   Cleanup is first because failure to enforce image retention can exhaust
   storage. Each step has an explicit timeout and records its own outcome and
   duration. A failure or timeout is accumulated but never prevents later
   steps from being attempted. The sequencer reports aggregate failure only
   after every step has run. A lock prevents overlapping sequences.

4. Complete recovery observability. Expose worker health and restart evidence,
   PostgreSQL availability, maintenance step and sequence outcomes, database
   restore outcome and duration, and the timestamp of the latest successful
   recovery. Add corresponding Grafana panels and actionable failure states.

5. Validate recovery in controlled drills after a quiet baseline: terminate
   one worker and confirm independent Compose restart; restart PostgreSQL and
   confirm worker reconnection without dump restoration; validate a selected
   dump in an isolated database; run the explicit restore procedure only with
   operator approval; and perform a VM-reboot drill confirming that the stack,
   workers, health endpoints, and maintenance timer return.

6. Add checkpoint-13 history, manual validation, production deployment and
   secret-path documentation, including exact inspection, stop, restart,
   backup, restore, and rollback commands.

- Add Prometheus Alertmanager email notification as a checkpoint-13 extension,
  after the core restart and recovery path is validated. Alert on persistent
  worker unavailability or repeated restart, PostgreSQL unavailability,
  failed maintenance or backup, and dangerous host disk or memory pressure;
  send a resolved notification when the condition clears. Use persistence
  delays so transient failures do not generate unnecessary mail.
- Keep Alertmanager SMTP credentials and addresses outside Git. Before email
  notification is implemented, the operator must create the ignored,
  mode-0600 file `.secrets/alertmanager_addresses.env` containing only:

      ALERT_EMAIL_TO=recipient@example.org
      ALERT_EMAIL_FROM=sender@example.org

  SMTP host, port, username, and password configuration remains a separate
  implementation step; the password must use its own ignored secret file and
  must never be placed in the addresses file or committed.
- Treat complete VM loss separately from in-VM alerts. A stopped VM cannot
  send its own failure email, so reliable VM-death notification requires an
  external Prometheus/Alertmanager, uptime service, or heartbeat observer.
  Prepare a heartbeat target and document this requirement, but leave the
  choice and deployment of the external observer outside the initial local
  Alertmanager implementation.

Checkpoint 14 - Distributed Windy worker scaling
------------------------------------------------

Objectives:

- Evaluate whether Windy throughput is constrained per API token, source IP,
  or VM rather than by a provider-wide backend.
- Run Windy ingestion from at least two VMs with distinct source IP addresses
  and distinct authorized Windy tokens.
- Partition the Windy source-stream set deterministically so that one active
  worker owns each camera and no camera is processed concurrently by two VMs.
- Keep PostgreSQL as the shared authoritative registry and ingestion-state
  store.
- Give each worker a stable identity and separate health/metrics target.
- Retain the validated 0.01-second request-start pacing per VM initially.
- Bound and compare database connection pressure across the single-VM and
  multi-VM configurations.
- Compare aggregate epoch duration, completed checks, publications,
  freshness-query errors, explicit throttling, external/S3 throughput, and
  provider-marker-to-download P50/P95 latency.
- Accept distributed operation only if aggregate throughput or latency
  improves materially without duplicate ownership, higher failure rates,
  database contention, or provider-policy violations.

Expected validation:

- Demonstrate that the configured partitions are disjoint and cover the
  intended Windy scope.
- Stop one VM and confirm that its partition is not silently processed by
  another worker unless an explicit reassignment is performed.
- Compare an equivalent single-VM baseline and two-VM run over the same
  observation duration and workload.
- Record token/API-policy assumptions without committing credentials.

Final pilot acceptance criteria
-------------------------------

- All three providers maintain a stable, persistent registry.
- Providers operate in the required Windy, Fintraffic, Skaping implementation
  order and can run independently.
- Unchanged provider images do not create duplicate derived images.
- Accepted images are validated, transformed, stored, and notified using
  versioned contracts.
- MQTT publication occurs only after successful S3 storage.
- PostgreSQL remains the authoritative registry and ingestion-state store.
- Credentials remain outside Git and are not written to logs.
- Discovery, ingestion, cleanup, and backup are observable and recoverable.
- Every checkpoint has a recorded synthesis and owner-executed validation.
