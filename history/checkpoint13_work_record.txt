Checkpoint 13 work record
=========================

Status
------

Implementation and automated validation are complete. The owner-operated
90-minute unquiet run, VM reboot drill, and any approved live restore remain
acceptance activities.

Implemented scope
-----------------

- Docker Compose supervises independent ingestion workers with restart
  policies, health endpoints, resource limits, and network-specific readiness
  windows. Windy uses batched freshness and its bounded-minimum strategy.
- Systemd provides VM-boot integration and one daily non-overlapping trigger.
  Maintenance attempts image cleanup first, then three discoveries, then
  verified PostgreSQL backup and dump retention. Each step has a timeout and
  later steps still run after an earlier failure.
- `database.database_restore` lists canonical S3 dumps, verifies length and
  SHA-256, validates the custom archive, restores only an explicitly selected
  key, and validates schema/registry. Its `just` wrapper stops workers before
  live restore and restarts them only after success. There is no automatic S3
  restore.
- Restore preserves ingestion state, including
  `estimated_source_stream_period`; ordinary PostgreSQL restart reuses the
  persistent volume.
- Prometheus/Grafana cover worker availability and restart evidence,
  maintenance step/aggregate outcomes, and database restore outcome/duration.
- A reproducible 90-minute runner injects a Windy crash, PostgreSQL restart,
  and concurrent cleanup-first maintenance while other workers continue.

The first owner launch revealed that `docker compose kill` counts as an
explicit operator stop and therefore correctly suppresses `unless-stopped`.
A second launch showed that an internally issued SIGKILL did not terminate the
namespace PID 1 and that checking health alone could accept the old process.
The drill now sends SIGTERM internally and requires both an increased Docker
restart count and healthy status before continuing.

The second launch also found an old root-owned lock below `/run/lock`. The
maintenance sequence now defaults to a UID-specific lock in `/tmp`, and an
unopenable lock returns a distinct `lock_error` rather than the misleading
`already_running` outcome.

Safe validation already performed
---------------------------------

Restore unit tests cover canonical listing, archive validation, checksum
rejection, and key rejection. Maintenance tests prove cleanup precedes
discovery/backup, discovery failure does not suppress backup, and overlap is
rejected.

A real 3,989,050-byte S3 dump was downloaded and verified against its stored
SHA-256. It was restored into a disposable PostgreSQL database; schema and
registry validation succeeded and the disposable database was removed. The
live database was never replaced.

Operational acceptance
----------------------

Follow `manual_tests/validation_to_complete_checkpoint13`. A live restore is
optional and needs separate approval because it replaces live database data.
