Checkpoint 8 work record - Fintraffic discovery
================================================

Status
------

Implemented and locally validated on 2026-07-23.
Checkpoint 8 is limited to Fintraffic station/preset discovery and registry
reconciliation. It must not download camera JPEGs, evaluate ETags, transform
images, write S3 objects, or publish MQTT notifications; those belong to
Checkpoint 9.

Provider model and scope
------------------------

- Network `fin` represents Fintraffic weather cameras.
- One provider station is one registry site.
- One station preset is one source stream.
- Only stations whose `collectionStatus` is `GATHERING` are eligible.
- Only presets whose `inCollection` value is exactly `true` are active
  discovery candidates.
- The selected rendition is `full_jpeg`, but discovery does not retrieve that
  JPEG.
- Fintraffic is a Finnish national provider. Registered sites use country
  `FI` after provider-value normalization/validation.
- The provider application identifier is sent in the `Digitraffic-User` header.
  It is required and non-secret, but must still be excluded from noisy request
  dumps and exception text.
- This corrects the older `Fintraffic-User` spelling in the architecture
  background: current official Digitraffic instructions specify
  `Digitraffic-User`, and the live endpoint was validated with that header.

Implemented provider access
---------------------------

The authoritative initial snapshot is:

    GET https://tie.digitraffic.fi/api/weathercam/v1/stations
    Digitraffic-User: <application identifier>
    Accept-Encoding: gzip

The response must be a GeoJSON-like `FeatureCollection` containing a
`features` array. Each accepted feature must have:

- a non-empty stable station identifier;
- Point geometry with finite longitude and latitude in valid ranges;
- a properties object;
- a `collectionStatus` value;
- a presets array whose accepted entries have a non-empty stable preset ID and
  `inCollection = true`.

The complete list endpoint establishes the authoritative station set and
eligibility. Because its compact presets contain only `id` and `inCollection`,
discovery then retrieves the detail endpoint for every eligible station.
Those paced requests populate station metadata such as `purpose`, camera type,
collection interval, municipality, province, and road address, and preset
metadata such as `presentationName`, `direction`, resolution, and image URL.
Any missing or malformed required detail aborts the complete run before
reconciliation, preserving the all-or-nothing snapshot rule.

HTTP access uses a finite timeout, a reusable client, explicit
`Digitraffic-User` and gzip headers, controlled retry/backoff for transient
responses, and response validation. A malformed or incomplete top-level
snapshot aborts reconciliation rather than inactivating valid stored streams
from a partial response.

Normalization and identifiers
-----------------------------

- Site identifiers follow `fin{station_id}`.
- Source-stream identifiers follow
  `fin{station_id}PRE{preset_id}`.
- Provider components are sanitized to the existing alphanumeric registry
  character set. Empty sanitizations and collisions are handled
  deterministically and tested.
- `provider_site_id` stores the raw station identifier.
- `provider_source_stream_id` stores the raw preset identifier.
- The complete normalized station feature/properties snapshot is retained in
  site `provider_metadata`.
- The complete normalized preset snapshot is retained in source-stream
  `provider_metadata`.
- Provider metadata must not contain internal registry state.
- GeoJSON coordinates are read in longitude, latitude, optional altitude
  order. The observed provider altitude `0.0` is not considered reliable:
  the raw coordinate remains in provider metadata, while registry altitude is
  left null unless a provider value is explicitly validated as meaningful.
  The shared altitude-enrichment lifecycle may then fill the registry value.

Registry reconciliation
-----------------------

The workflow builds a complete in-memory `DiscoveredSite` /
`DiscoveredSourceStream` snapshot and reuse
`database.registry_queries.apply_discovery_update`:

- new stations and presets are inserted;
- existing metadata is replaced by the current normalized provider snapshot;
- an inactive preset that becomes eligible again is reactivated;
- a previously registered preset absent from the complete eligible snapshot,
  under a non-gathering station, or with `inCollection != true` becomes
  inactive;
- discovery never overrides `blacklisted`;
- no provider entity is physically deleted;
- one transaction reconciles the complete snapshot;
- `--dry-run` retrieves, validates, normalizes, and compares without writing.

Repository structure
--------------------

    discovery/fintraffic/__init__.py
    discovery/fintraffic/fintraffic_source_access.py
    discovery/fintraffic/fintraffic_discovery_workflow.py
    tests/discovery/fintraffic/

`config/deployment_config.py` will expose a validated non-empty
`FINTRAFFIC_USER_HEADER`, provider timeout/retry settings, the selected
station status `GATHERING`, the `inCollection` requirement, and the
`full_jpeg` rendition. `.env.example` may contain a non-sensitive example
placeholder but no credentials.

Automated coverage
------------------

- required request headers and endpoint;
- valid FeatureCollection parsing;
- malformed top-level, station, geometry, coordinate, properties, preset-ID,
  and `inCollection` values;
- station and preset filtering;
- deterministic stable identifiers, sanitization, and collision handling;
- longitude/latitude ordering and unreliable zero-altitude handling;
- preservation of station and preset provider metadata;
- duplicate station/preset rejection or deterministic deduplication;
- transient HTTP retry/backoff and terminal error behavior;
- dry-run non-mutation;
- transactional insert/update/inactivate/reactivate behavior;
- blacklist preservation and repeated-snapshot idempotency.

Validation evidence
-------------------

Focused Fintraffic, Windy-regression, and deployment-configuration tests:

    49 passed

Shared PostgreSQL registry integration tests:

    11 passed

The complete live dry run observed:

- 813 provider stations, of which 809 were gathering and 4 excluded;
- 2,276 presets, of which 2,255 were in collection and 21 excluded;
- 809 normalized sites and 2,255 normalized source streams;
- no registry write.

After detailed metadata retrieval was made mandatory, the same live dry run was
repeated successfully with one list request and 809 paced station-detail
requests. It completed in about 147 seconds and produced the same 809-site,
2,255-stream eligible snapshot while adding the descriptive detail fields to
the normalized JSONB metadata.

The subsequent owner-applied discovery was verified from PostgreSQL: all 809
sites have `purpose`, municipality, province, road-address metadata, and a
derived altitude; all 2,255 active presets have `presentationName`, direction,
resolution, and image URL metadata.

The first applied run inserted 809 sites and 2,255 streams. It activated or
inactivated no existing streams and preserved the complete eligible snapshot.
Shared altitude enrichment resolved and updated 600 sites; 209 unresolved sites
remain eligible for a later discovery run.

The immediate second applied run inserted no sites or streams and performed no
activation or inactivation. It refreshed metadata for the same 809 sites and
2,255 streams, proving stable identifier assignment and registry membership for
an unchanged provider snapshot. The 209 still-missing altitudes were retried
and remained unresolved.

SQL inspection confirmed 809 distinct `fin` sites, 2,255 active streams, no
inactive or blacklisted Fintraffic streams, plausible longitude/latitude
ordering, `full_jpeg` rendition, and identifiers such as
`finC01503PREC0150301`.

Operational commands
--------------------

    just discover-fintraffic --dry-run
    just discover-fintraffic
    just discover-windy --dry-run
    just discover-windy

Both recipes forward workflow options. Fintraffic discovery uses one complete
station-list request followed by one paced detail request for each eligible
station.

Checkpoint decision
-------------------

Checkpoint 8 was accepted by the owner on 2026-07-23 after the detailed
discovery was applied and its registry metadata verified. Checkpoint 9
Fintraffic ingestion remains outside checkpoint 8 and is recorded separately
in `history/checkpoint9_work_record.txt`.

Later checkpoint 9 live ingestion validation observed 2,263 presets with a
non-null `measuredTime` in the provider station-data snapshot. This is a live
freshness-snapshot count, not a correction to checkpoint 8's point-in-time
2,255-stream eligible discovery result: discovery remains authoritative for
which registered streams are scheduled, while ingestion may observe additional
provider entries or entries whose collection eligibility has changed between
discovery passes.
