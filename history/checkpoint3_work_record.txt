Checkpoint 3 work record - Windy discovery
============================================

Outcome
-------

Checkpoint 3 is complete. It implements Windy Webcams API v3 discovery for
the 33 EUMETNET member countries and reconciles complete discovery snapshots
with the shared PostgreSQL registry. It does not download or transform webcam
images; that begins in checkpoint 5 after checkpoint 4 altitude enrichment.

Implementation
--------------

- config/deployment_config.py loads non-secret Windy settings and reads the
  API key from an ignored file.
- discovery/windy/windy_source_access.py performs authenticated, timed, and
  paginated requests with 0.1-second configurable pacing, bounded retry and
  backoff for throttling, response validation, daily resumable caching, and
  deduplication by Windy webcam identifier.
- Discovery first queries totals for all 33 member countries. Countries with
  at most 1,000 results use complete country pagination. Larger countries use
  configured geographic discs because the provider listing is capped.
- The committed coverage uses 40 km discs for AT, CH, CZ, DE, ES, GB, IT, and
  NO, and 50 km discs for FI and FR. The other 23 countries use country
  listings.
- discovery/windy/windy_discovery_workflow.py normalizes metadata, restricts
  results to member countries, excludes indoor cameras, preserves identifiers
  and existing site assignments, infers new sites conservatively by distance,
  supports --dry-run, and delegates writes to the checkpoint 2 transactional
  registry layer.
- Provider metadata, including Windy's status field, is retained in the
  source_stream provider_metadata JSONB object.
- Windy's status field is deliberately ignored when deciding registry
  eligibility. Live tests showed that it fluctuates between consecutive API
  responses for cameras that remain discoverable.
- Tools were added to count member-country totals, generate and inspect disc
  coverage, compare country and disc results, and report discovery stability.

Safety and consistency properties
---------------------------------

- The API key is sent only in the X-Windy-API-KEY header and is never included
  in raised error messages or committed files.
- Any failed query, changed pagination total, or incomplete page aborts the
  complete discovery before registry reconciliation.
- Overlapping disc results are deduplicated by provider webcam identifier.
- Existing source-stream identifiers and inferred-site assignments take
  precedence over a new proximity calculation.
- Registry reconciliation is transactional and never automatically overrides
  blacklisted streams.
- A dry run retrieves and compares a complete snapshot but cannot modify the
  database.

Validation performed
--------------------

- The focused offline suite passed: 25 unit tests.
- The live PostgreSQL integration suite passed: 7 tests.
- A clean first discovery registered 25,030 Windy streams.
- An immediate second pass over the same provider snapshot inserted no sites
  or streams and produced no activation changes.
- A later fresh live pass found 47 previously unseen provider IDs and did not
  find 18 stored IDs. The next fresh dry run returned exactly the same 25,059
  IDs as that preceding snapshot: zero additional IDs and the same 18 absent
  IDs.
- Those results show short-term stability after ignoring provider status, but
  not a guarantee that Windy's listing membership is invariant over time.
- The final dry-run comparison did not write to PostgreSQL.

Operational interpretation
--------------------------

Windy discovery is provider-specific and should be treated as a changing
snapshot. A webcam missing from a complete snapshot currently follows the
shared registry rule and becomes inactive. If repeated live operation shows
frequent listing disappearance and return, a later change may introduce a
Windy-specific intermediate or grace status so ingestion stops querying the
camera without treating one absence as a permanent removal. That behavior is
not part of checkpoint 3.

Checkpoint decision
-------------------

Checkpoint 3 is accepted. Proceed to checkpoint 4 only after reviewing this
record and the corresponding manual validation record. Checkpoint 4 adds
shared site-altitude enrichment before image acquisition begins.
